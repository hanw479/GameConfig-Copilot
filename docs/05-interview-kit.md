## 2. 电梯陈述

**30 秒**

> 游戏策划配一个任务要在 Wiki、旧配置、数值约束之间来回翻，重复且容易错。我做的系统让策划用一句话描述需求，Agent 先检索依据，生成结构化任务配置，再跑三层校验，通过后生成 diff 让人确认，确认了才原子写入并备份。核心不是生成，而是"有依据地拒绝"和"可审计地执行"。

**2 分钟**（在 30 秒基础上加）

> 架构上分四层：FastAPI 做流式交互；LangGraph 做 Supervisor 路由，QueryAgent 只有检索工具，TaskAgent 才有生成和写入工具，工具集最小化；RAG 层把检索单元切到"可复用的配置片段"，用 RRF 融合稠密和稀疏检索；MCP 层是 Agent 的手，默认只读，写入要过指纹、版本号、强制复检、原子替换、备份五道关。评测上分三层：检索看 Recall 和 MRR，问答看 Ragas，Agent 看首次通过率和危险拦截率，每次改动都能对比基线回答"提升了多少"。

## 3. 高频追问

### Q1：为什么不做一个"万能 Agent"，要拆成两个？

**要点**：工具集越大，模型选错工具的概率越高；写权限应该只存在于真正需要它的 Agent 上。

> 单 Agent 同时挂检索、生成、写文件十来个工具，Prompt 长、误调用多，而且一旦被注入就可能直接触发写工具。拆开之后 QueryAgent 在工具注册层面就拿不到写工具，这是权限隔离而不只是 Prompt 约束；另外两个 Agent 可以分别评测，检索不准和生成不准不会混在一起。

**追问"多一次路由是不是浪费"**：路由用小模型 + 规则，成本不到总调用的 5%；换来的是可解释的失败定位。

---

### Q2：MCP 和 Function Calling 有什么区别？为什么不用纯 Function Calling？

**要点**：Function Calling 是"模型怎么表达调用意图"，MCP 是"工具怎么被组织和暴露"。

> Function Calling 解决的是模型输出结构化调用参数的问题；MCP 是协议层，把工具做成独立服务，有标准契约、能跨进程、能被不同客户端复用。我这个项目里如果只用 Function Calling，工具和 Agent 强耦合，没法单独做只读部署，也没法让轨迹面板或 IDE 复用同一套工具。用 MCP 之后，我可以把服务以只读模式启动，工具列表里干脆没有 `commit`，这是部署态的安全边界。

**追问"那 MCP 的代价"**：多一层序列化和进程管理，调试链路变长；所以我在工具内部统一返回结构化错误，不让异常穿进程边界。

---

### Q3：检索不准，你怎么排查？

**要点**：分层拆，先定位是"没召回到"还是"召回了没用对"。

> 我按四层排查：第一层看 query 理解，术语有没有归一（比如"矿洞/矿车"要映射到同一个地图 ID）；第二层看过滤条件，等级段或类型过滤是不是把正确片段挡掉了；第三层看召回，分别看 dense 和 BM25 各自的命中，判断是语义没匹配上还是关键词没命中；第四层看排序，RRF 之后 top-5 里有没有相关片段，有的话就是排序问题，没有就是召回问题。定位之后再做针对性优化——改写、调过滤、换切分、加 reranker，每次改动都用 Recall@5 和 MRR 对比基线，不靠感觉。

---

### Q4：草案第一次没通过校验，怎么办？

**要点**：把结构化错误回灌给模型修复，限轮次，失败就交还人工，绝不绕过校验。

> 校验返回的是结构化的 `ValidationReport`：错误码、字段路径、约束来源、建议值。修复节点把这些连同原始需求和约束原文一起回灌，让模型只改出错字段，最多两轮。两轮还不过就进入 `rejected`，把错误原样解释给策划，让人来改。关键设计是：修复只走"重新生成 + 重新校验"，没有任何"跳过校验"的开关。

**追问"修复会不会改坏别的字段"**：修复后草案整体重新校验，不是只校验出错字段；指纹也会重新计算，旧确认失效。

---

### Q5：怎么保证 Agent 不改坏文件？

**要点**：五道关，且最后一道不依赖模型。

> 一，MCP 默认只读，写模式是启动参数，不是运行时能开的；二，路径白名单，只允许 `data/tasks/**`，拒绝 `..` 和软链；三，两阶段提交，预览时给草案算指纹，确认时必须带同一个指纹和文件版本号，防止"确认的是 A、写的是 B"；四，提交时内部再跑一遍完整校验，不信任上游结论；五，同目录临时文件 + `os.replace` 原子替换，替换前先备份，审计日志记录 diff。任何一步失败，目标文件一个字节都不动。

**追问"进程崩了怎么办"**：替换是原子的，要么旧要么新；临时文件启动时清理；备份可以回滚。

---

### Q6：评测指标怎么设计的？为什么是这几个？

**要点**：按层归因，指标要能回答"哪一层退化了"。

> 分三层。检索层看 Recall@5 和 MRR，回答"依据找没找到"；问答层看 Ragas 的 faithfulness 和 context_recall，回答"回答有没有胡说"；Agent 层看首次通过率、平均修复轮次、危险拦截率、P95 延迟和单次成本，回答"产品能不能用、安不安全"。另外专门做对抗集，5 条必须全部拦截，这是红线指标，不是平均分。所有指标都固定数据集和 judge 模型，只做相对比较。

**追问"30 条够吗"**：不够做统计显著性，但足够发现方向性回归；我把它当回归测试而不是学术评测，指标下降超过阈值就阻断合并。

---

### Q7：怎么避免幻觉？引用会不会是假的？

**要点**：引用来自检索结果的结构化 ID，不是模型自由生成的字符串。

> 检索返回的每条片段都有 `source_id + chunk_id`，模型只能从给定列表里选，回答里的引用会在后处理时校验 ID 是否存在，不存在就降级为"未找到依据"。另外系统提示明确要求"没有依据就说没有"，并在评测里专门放知识库外的问题，看它会不会编。

---

### Q8：为什么用 LangGraph？和 LangChain 的 AgentExecutor 比呢？

> 我需要的是显式状态机：什么时候等人确认、失败重试几次、中断后从哪恢复。AgentExecutor 是黑盒循环，人工确认这种中断点不好插，也不好单步调试。LangGraph 把节点和边画出来，每个节点可以单测，`interrupt` 天然适配"预览后等确认"。代价是要自己管状态结构，但换来的是可控性。

---

### Q9：成本和延迟怎么优化？

> 延迟上，检索和校验都是本地毫秒级，大头是生成；做法是限制上下文预算（6000 token，按区块分配）、只放 top-2 相似任务、流式返回首 token。成本上，路由用小模型，生成用主力模型，校验不调用模型；评测阶段用录制回放，避免重复烧钱。指标里 P95 延迟和单次成本都进回归，涨超 20% 会告警。

---

### Q10：如果真要上生产，还缺什么？

> 四块：权限与身份（现在只有工号，生产要接 SSO 和审批流）、发布链路（现在只写工作区，生产要接分支/灰度/回滚）、并发与多租户（文件锁只适合单机，生产要换成配置中心或数据库事务）、可观测（自研 JSONL 要接 OTel 和告警）。这些我在文档里列为非目标，但能说清边界和演进路径。

---

### Q11：你的 RAG 和通用的文档问答 RAG 有什么不同？

> 检索单元不同：通用 RAG 切段落，我切的是"可复用的配置片段"——一条任务模板、一个奖励区间、一段对白示例，并且保留父块回链，生成时能"抄结构"。检索目标也不同：不是给人读得懂，而是给 Agent 抄得对，所以召回精度优先于回答流畅度。另外检索结果要参与校验，比如引用必须真实存在，这反过来约束了检索质量。

---

### Q12：那个"1 级任务 1000 金币"的演示，想说明什么？

> 说明 Agent 不是顺从型工具。它检索到数值约束后拒绝写入，并解释依据来自哪条规则、上限是多少、有哪些合规替代方案。这背后是三个设计：约束显式化（不是模型记忆）、校验确定性（不靠模型自检）、写入有闸门（拒绝时零写入）。我认为这比十个成功案例更能说明工程成熟度。

## 4. 指标口径（防止被追问翻车）

| 指标 | 分子 | 分母 | 说明 |
| --- | --- | --- | --- |
| FPVR | 首次生成即通过全部校验的需求数 | 30 条黄金需求 | 人工确认不算在内；修复后通过不算首次 |
| 平均修复轮次 | 所有失败样本的修复轮次之和 | 失败样本数 | 通过样本不计入 |
| 危险拦截率 | 被正确拦截的对抗样本数 | 5 条对抗样本 | 误放行一条即视为失败 |
| Recall@5 | 前 5 命中中含相关片段的 query 数 | 20 条标注 query | 多相关片段时按命中任一计 |
| P95 延迟 | 从请求到 `awaiting_confirmation` | 30 次采样 | 不含人工确认等待 |

**自查**：简历上每个数字，都要能在 `docs/reports/` 找到对应报告。
